# Is there an Interaction Model? What survives between the Event Model and the pixels

> **Position:** There is no Interaction Model stratum to add to xmlang. There is a *derived* one: a set of navigation and enablement facts that follow from the Event Model and that the spec should state as Defaults so every transformer computes them the same way. What a designer adds on top is small: one friction bit per command (`confirm`), one return-to-worklist name per command (`then`), and copy. Everything else the literature calls an interaction judgment turned out to be the Event Model itself, geometry in disguise, a design-system-wide rule and not a per-action choice, or a label. That is, item for item, what survived thirty years of Model-Based UI: a convention-default, one flat attribute, and the behaviour model as a state × event table.

## 1. The question, and why now

The [xmlang specification](xmlang-spec.md) stops at surfaces. It records which personas exist, which views and commands share a surface, how salient each field is, which phases a surface is active in, and what things are called. It says nothing about how surfaces connect, what the user sees after a command, whether a command asks before it acts, or which of several surfaces a viewer stands on inside one `during` × `for` cell. The spec calls that last one "deliberately NOT expressible" and hands it to "a hand-written selector in the concrete stratum". The shipped interpreter behind the three kvissig games has exactly such a selector, written three times.

So the open question after [the first research article](machine-readable-ux-specs-research.md) and [the geometry experiment](xmlang-geometry-experiment.md) was whether a third stratum sits between the Event Model (behaviour) and the concrete UI (geometry and idiom): an Interaction Model that records genuine judgment as data. "Interaction model" turns out to carry three senses, and all three were in scope:

- **A. Navigation topology**, the information-architecture sense: how surfaces connect, where a command lands the user, entry surfaces per persona.
- **B. Dialog or state model**, the MBUI sense: what the user can do at each moment, enablement, transitions.
- **C. Interaction idioms** per command or view: confirm, undo, optimistic versus confirmed feedback, inline versus modal, wizard versus single form, read-only versus editable posture.

Two things fixed the shape of the inquiry. First, the target: xmlang is optimised for line-of-business enterprise software (the spec's own examples are invoices, accountants, month-end close), and the three party games that are its only shipped testbeds are a negative control, not the population. A judgment absent from a two-persona quiz says nothing about accounts payable. Second, the method: the geometry experiment settled a vocabulary question by fixing hypotheses, a rubric and tripwires before any evidence, and by treating "the annotation restates a default" as a failure. I reused that method. Eleven agents worked in three phases (literature and derivability, per-sense analysis, red team and implementation cost), and this article is the write-up of their decision record.

## 2. What MBUI called a dialog model, and why it died

Every Model-Based UI dialect had two dialog-ish constructs, never one. At the task level sat a temporal algebra (ConcurTaskTrees' `>>`, `[]`, `|||`, `[>`, LOTOS-derived) that re-described the system's behaviour. At the presentation level sat a state machine: UIDE's pre- and post-conditions, Cameleon's transition tasks, UsiXML's Event-Condition-Action rules, MARIA's per-presentation dialog with conditional connections, the W3C Abstract UI's `AbstractListener`. The first duplicated the application's own behaviour model. The second grew into a programming language. Neither was ever the small residue I was hoping to find.

Navigation was almost never authored. Cameleon derived it: Enabled Task Sets grouped by heuristics into Presentation Task Sets, connected by rules of the form "(transition_task, next_PS)… when transition_task is executed, the abstract user interface passes from P to next_PS" ([Cameleon D2.1 §1.2.3](http://giove.isti.cnr.it/projects/cameleon/doc/CAMELEON%20D2.1.pdf)). The same document admits the derivation was too crude ("a direct mapping between enabled task sets and user interface presentations can generate excessively modal user interfaces") and that "the designer can override the default navigation scheme". The judgment lived in tool heuristics and hand overrides, never in the model. That is direct evidence for the hypothesis that navigation is mostly derivable with a small residue; it is also a warning about where the residue ends up.

Myers, Hudson and Pausch's verdict covers the whole family: "Programmers must also learn a new language for specifying the models, which raises the threshold of use. In addition, model based systems have a low ceiling", and "the generated user interfaces were generally not as good as those that could be created with conventional programming techniques" ([Myers 2000 §2.3.4](http://www.cs.cmu.edu/~amulet/papers/futureofhci.pdf)). The literature report distilled nine recurring failure mechanisms; the four that matter for this inquiry are:

| | Mechanism | Exhibited by |
|---|---|---|
| F1 | The dialog model becomes a programming language: the moment a `when:` or condition appears, the predicate language has to grow to whatever the product needs | UIDE, UsiXML, MARIA, W3C AUI |
| F2 | The task model duplicates the behaviour model. Foley, quoted by Schlungbaum: "some information has to be specified twice, once by the software engineer and once by the user interface designer" ([Schlungbaum 1996](https://repository.gatech.edu/server/api/core/bitstreams/40d91981-35ff-4759-a792-93afd8ba23bb/content)) | every task-model-driven dialect |
| F3 | Abstract containers are geometry in disguise: ARTStudio workspaces mapped to window or canvas by navigation interactor | Cameleon, TRIDENT, UsiXML |
| F9 | Interaction-type taxonomies restate the data type (selection, editing, activator) and are dead weight | CTT, MARIA, W3C AUI |

The others (derived navigation too modal, combinatorial context adaptation, unpredictability, moving targets, standards without implementers) are in the [full report](#11-where-the-evidence-is).

What survived writes down exactly three dialog or navigation facts as data. Statecharts (Harel, SCXML, XState, [statecharts.dev](https://statecharts.dev/use-case-statecharts-in-user-interfaces.html)) keep a state × event → next-state table with no presentation in it; they survived by *being* the behaviour model rather than annotating it. [Figma prototype flows](https://help.figma.com/hc/en-us/articles/360040035874-Prototype-actions) keep a trigger → destination graph drawn on the pixels, and have already grown `Set variable` and `Conditional`, which is F1 in miniature. Rails keeps a post-command destination as a *convention* (`redirect_to @record` after create, `render :new` on failure, [Rails guide](https://guides.rubyonrails.org/getting_started.html)), overridable in one line. And [htmx](https://htmx.org/docs/) keeps a handful of flat, closed, per-control attributes (`hx-confirm`, `hx-target`, `hx-swap`) while enablement moved back to the server: "the server tells the client what it can do next." None of the survivors is an abstract container, none has a task algebra, and the two that grew conditionals are the two on the slope.

## 3. The method

Five admission tests were fixed before any evidence was collected. A candidate vocabulary item enters xmlang only if it passes all five:

1. **Derivability.** It is not computable from the Event Model alone (slices, command → event → view chains, `phase`, swimlanes, GWT scenarios). If it is derivable, it is a Defaults-table entry, not vocabulary.
2. **Dead weight.** At least one genuine non-default annotation on a representative LOB model. The games are a secondary check: dead weight on both fails; dead weight on the games alone does not.
3. **Geometry leak.** It names a judgment (membership, ordering, tier, closed enum), never a position, container, region or breakpoint, including disguised geometry such as `modal` or `drawer`.
4. **Slope.** The key does not demand a second key to do any work.
5. **Transformer neutrality.** It means something to a code generator, a runtime interpreter, and a human or agent hand-building UI.

Three bodies of evidence were assembled against those tests.

**The residue catalogue.** Every interaction decision the concrete code makes that the spec pair does not fix, across the three shipped games and their shared interpreter: 62 decisions, each with a file and line. About 45 of them are identical in all three games, written as near-verbatim copies in three sister files. That is the signature the geometry experiment used to call an annotation dead weight: the live product *is* the default transformer, so no annotation could differ from it. The residue that varied was small: who paces progression (system, host, or player), which field titles a surface, sort order of a scoreboard, and a cluster of copy the `labels` block could not key.

**The LOB testbed.** A 33-slice accounts-payable Event Model and a matching Experience Model (`lob-ap.em.yaml`, `lob-ap.xm.yaml`), valid under `em parse` and `xm lint`. It has five swimlanes (Clerk, Approver, Controller, Admin, System) and two deciders: `State / Invoice` with nine phase values from `draft` to `discarded`, and `State / Supplier` with an active/inactive lifecycle. It contains drafts, submission and withdrawal, approval with a per-approver limit and a four-eyes rule, bulk approval, dispute holds, payment scheduling and a nightly payment run, voiding with a compensating ledger event, stale-approval reminders, and optimistic concurrency on every edit. The Experience Model has four personas, 24 surfaces and seven journeys; the `Invoice details` view is composed a dozen times across the `during` × `for` lattice, which is the LOB shape of the games' host/player surface pairs at scale. I want to be plain about its status: it was constructed by this team for this inquiry, and no transformer has rendered it. Section 10 returns to that.

**The games as negative control.** A key that does real work on accounts payable should be inert on a party auction, and a key that fires on the games should be suspected of restating a default.

## 4. Sense B, dialog: zero vocabulary

The hypothesis was that the dialog model already lives in emlang and anything xmlang could add is derivable or a `when:` in disguise. It held, and more strongly than the spec admits.

Start with the selector the spec calls inexpressible. Inside the `started` phase of an auction, a player stands on one of three surfaces: the bid form, the waiting screen, or the round results. The interpreter decides with a hand-written function: results if the lot is resolved, waiting if the viewer has already bid, otherwise the form. Six independent implementations of that function exist (the three sister files in the interpreter and the three clean-room probe prototypes from the geometry experiment), and all six compute the same thing. Convergence of that kind is the signature of a derivation, not a judgment. The derivation is this: read the phase's slices in order; each state-change slice ends in the view the actor sees next; a viewer's position is the terminal view of the last slice whose event fired *for her*. Her own command's event moves her (`BidPlaced` → `Bid progress`, the waiting surface). A System processor's event moves everyone (`LotRevealed` → `Round scores`). Another persona's event moves her (`StartAuction` → `Lot card`). A same-persona peer's event does not (another player's `BidPlaced` leaves her on the form). The surface is the one in the cell composing that view for her persona.

| Implementation | Resolved → results | Own bid → waiting | Else → input | Unknown viewer |
|---|---|---|---|---|
| BlindBudet interpreter (`AuctionSurfaces.cs`) | yes | yes | yes | input surface |
| Mer eller mindre interpreter (`GameSurfaces.cs`, one extra stage) | yes | yes | yes | input surface |
| Tänk till tusen interpreter (`TankSurfaces.cs`) | yes | yes | yes | input surface |
| Clean-room probe run 1 | yes | yes | yes | join form |
| Clean-room probe run 2 | yes | yes | yes | "you missed this one" message |
| Clean-room probe run 3 | yes | yes | yes | join form |

Six of six agree on every branch the Event Model determines; they diverge only on the branch it does not (a viewer with no identity), which is exactly where a stated default earns its keep. On the LOB model the derivation degenerates: every `during`-bound cell holds one record surface per persona, so the per-viewer cursor is never exercised and the rule reads "the one surface in the cell". It is needed only in synchronous multi-actor cells (the games; parallel approvals if a model has them).

Enablement is the same story with a twist. The Event Model carries guard *names* (`x: NotEnoughPlayers`, `x: AlreadyBid`, `x: CannotApproveOwnInvoice`) and decider-true scenarios for each; the predicate itself is decider code. The interpreter's `players.Count >= 2` before it shows the Start button is a hand copy of the guard, F2 in miniature. But a Defaults row can say what to do with a guard that would reject without xmlang ever holding the predicate: render the command disabled with the blocking exception's label, never hidden by state alone (hiding by role is what `for:` is for). And the LOB model showed the stronger pattern: per-viewer enablement moved into the read model. `Approval queue` projects `pending` versus `blocked` per approver, so the four-eyes rule and the approval limit never need a predicate in the Experience Model. The view already tells the viewer what she can act on. Enterprise read models routinely absorb this; games rarely bother.

So the `when:` rejection stays, but its justification changes. The spec rejects `when:` because every MBUI dialect that grew one drowned. The stronger reason is that it is *redundant*: fine selection is derived, and anything else a `when:` would express is a missing phase value, a missing command (an intent with no event, like the tap-through GET that leaves one game's reveal screen without writing anything), or a guard that belongs in the decider. Sense B admits zero vocabulary: two Defaults rows and a lint that checks compositions against the phase table (`xm-command-phase-mismatch`).

## 5. Sense A, navigation: mostly derivable, one residue

The hypothesis named three residues: entry surface per persona, return versus advance after a command, and wizard grouping. One survived.

Most of navigation fell out of the Event Model plus the Experience Model's existing document order. A persona's entry surface is the first surface in document order applicable to her with no `during`; her global navigation is the set that rule ranges over; `during`-bound surfaces are reached through destinations and links; a terminal-phase surface offers a return to entry. On the LOB file as first written, that rule got two of four personas wrong (Clerk and Controller both landed on the supplier directory), and reordering four surfaces fixed all four, because Admin is in none of the home surfaces' `for:` lists. Document order can express it; test 1 fails. The honest cost is that the judgment is positional and a reader must know the rule. That is the spec's own "order = importance" doctrine, and I accept it.

Links derive from identity lineage: a view field typed as another view's identity links to the surface composing that view for the persona. This is Dymitruk's information-completeness rule read as topology; every field has "the source of and destination of the information" ([eventmodeling.org](https://eventmodeling.org/posts/what-is-event-modeling/)). On the LOB model every list row's `invoiceId` and every `supplierId` resolved to exactly one view and, through `during` × `for`, exactly one surface. Wizard grouping was rejected twice over: a multi-step interaction that must survive partial completion is a draft, which is slices in the Event Model (the LOB model has `DraftInvoice` and `EditDraft`); chunking one command's ten props into header, lines and attachments is concrete; and groups need names, so the first instance demands a new labelable element, which is the slope.

The residue is the post-command destination. The default is derivable: after an accepted command, the surface applicable to the viewer's persona that composes the terminal view of the command's slice, in the new phase; if none exists or it is the issuing surface, stay; a rejected command re-presents the issuing surface. That is Rails' `redirect_to`, stated once. The sense A analyst, working on an accounts-payable model of his own construction, found the default wrong four times out of nine composed commands (submit → back to the inbox, approve and reject → back to the queue, void → back to the inbox). The red team re-ran the count on the real testbed:

| Count | Population | Genuine non-default `then` |
|---|---|---|
| Sense A, own model | 9 composed commands | 4 |
| LOB testbed report, real file | 24 state-change slices | 3 |
| Red team, real file | 21 composed commands | **2** |

Two of twenty-one: `SubmitInvoice` → `ClerkHome` (a proxy for "back to the worklist"; the designer actually wanted "the next draft", which no surface name expresses) and `VoidInvoice` → `ApproverHome`. The third case the LOB report had counted was not a `then:` case at all: the modeller had written `ApproveInvoice`'s slice to end in `Approval queue`, so the default already returned to the queue.

That last observation is the decisive objection, and I want to state it plainly rather than bury it. The one LOB modeller we have wrote destinations into each slice's terminal `v:`. Approve, reject and bulk-approve end in `Approval queue`; discard ends in `Invoice list`; everything else ends in `Invoice details`. In Event Modeling the terminal view of a state-change slice is what the actor sees next, so `then:` is a second home for the same fact, and nothing in the syntax says which wins when they disagree. This is F2 on xmlang's first edge.

`then: <Surface>` is admitted anyway, with amendments that follow from the objection. It is a *return*, never an advance: the advance is the Event Model's terminal view, and a `then` naming the surface that composes the terminal view restates the default (`xm-then-restates-default`, info, the dead-weight instrument). It must apply to every persona of the composing surface (`xm-then-persona-mismatch`, error); on the LOB model that rule forbids writing it on `CreateSupplier`, which three personas share, and only the default resolves per persona, which is the right outcome. Conditional destinations (`then-on-reject`) and instance destinations (`next`) are Non-goals: a rejected command always re-presents the issuing surface, and "advance to the next pending invoice" is a worklist view whose first row is the next item, or a command, never a destination value. Fiori's own configuration supports that split: `stayOnCurrentPageAfterSave` is stay-versus-return, while "Create Next" is a separate action ([SAP Fiori elements draft handling](https://raw.githubusercontent.com/SAP-docs/sapui5/main/docs/06_SAP_Fiori_Elements/draft-handling-ed9aa41.md)). The status of `then` is provisionally admitted pending a shipped LOB transformer run, with a tripwire: if a second LOB model shows terminal `v:` and `then:` systematically disagreeing, the fix is the Event Model and the key is withdrawn.

Two navigation facts belong to emlang, not xmlang. The trigger `t: Player /Lot` names an originating screen as free text; the parser keeps the lane and drops the name, and `Lot` does not resolve to the view `Lot card`. Making the origin a resolvable view reference turns destination, source, entry and topology derivations from heuristics into references. On the LOB model 18 of 18 human triggers name an existing view; on the games 1 of 12 does. And the true trigger set: all three games' Event Models say `Next lot` and `End auction` are System processors; all three shipped UIs give the host a button. The honest fix is `t: host /Round results` beside `t: ⚙️ System / Next lot`, after which the mutual exclusion of Next and End follows from the Todo gate and the enablement default.

## 6. Sense C, idioms: one bit

The interpreter's render model carries an optional record of eight "residue chrome slots" that every game fills the same way: `Heading`, `Sub`, `Footer`, `PollPath`, `PlayAgainHref`, `ShareText`, `Steps`, `Source`. That record is the interaction vocabulary the interpreter needed and the Experience Model lacked, so classifying it is the empirical answer to sense C. One slot is data (which field titles the surface). Five are copy or static content in one form or another: the templated sub-heading, the footer that explains a withheld command, the share text, the "how it works" steps, and the play-again link, whose target is a navigation default. One is transport (the poll path, a declared Non-goal). One is a gap in the Event Model (a `source` citation the `Question card` view does not carry). Zero are idioms. The planned enum of input idioms stalled at one entry (`Keypad`) and two games opted out to hand-written Razor instead: input idioms are concrete, and nobody wanted them as data.

`confirm: true|false` on a command item is the one clean admission. On the LOB testbed the designer wanted it on four of 21 composed commands: `DiscardDraft`, `VoidInvoice`, `ReversePayment`, `DeactivateSupplier`. The obvious attack is that confirmation is irreversibility in disguise and should derive from a `compensates:` link in emlang. Run the derivation: Void leads to a terminal phase and emits a compensating ledger event, derivably irreversible; Discard likewise. But `DeactivateSupplier` is undone by `ReactivateSupplier` and `ReversePayment` returns the invoice to `approved`, so the best derivation says no confirmation, and the designer wanted it anyway. Two of four survive the strongest derivation, and they are the interesting two: the reason is consequence to others (an inactive supplier blocks drafting; a reversal moves money), not reversibility. That killed the proposed default that a compensated command is offered without confirmation, and the lint that would have nagged on exactly the genuine cases.

Six enterprise design systems record this judgment per action: Fiori's `Common.IsActionCritical` ("Actions that require user confirmation are called critical actions", [SAP-docs](https://github.com/SAP-docs/sapui5/blob/main/docs/06_SAP_Fiori_Elements/adding-confirmation-popovers-for-actions-87130de.md), via search summary [S]); Carbon's danger modal "for destructive or irreversible actions" ([Carbon](https://raw.githubusercontent.com/carbon-design-system/carbon-website/main/src/pages/components/modal/usage.mdx)); Salesforce's `lightning-confirm` and destructive button variant ([Salesforce](https://developer.salesforce.com/docs/component-library/bundle/lightning-confirm)); Fluent's alert dialog "only in cases of potential loss" ([Fluent 2](https://fluent2.microsoft.design/components/web/react/core/dialog/usage)); Redwood's destructive message dialog ([Oracle](https://www.oracle.com/webfolder/technetwork/redwood/message-dialog-destructive-action.pdf), via search summary [S]); Atlassian's warning messages ([Atlassian](https://atlassian.design/foundations/content/designing-messages/warning-messages)). The games confirm nothing, including the irreversible `EndAuction`, and that is right for a party game: zero annotations in three files, the control passing. The form of assent (dialog, inline second step, typed re-entry) is transformer-defined, and an `impact:` tier is a Non-goal: degree of friction is a rendering of consequence, and `prominence: overflow` plus `confirm: true` is already the strong form. Habituation gets a lint (`xm-confirm-habituation`, warning, when more than half a surface's commands confirm; NN/g: ["if you cry wolf too many times, people will stop paying attention"](https://www.nngroup.com/articles/confirmation-dialog/)).

`heading: <field>` was proposed and killed. Two of three games title their input surface with a data field (the lot description, the question text) instead of the surface label, and the sense C analyst read that as a naming judgment, the accessible name of the page, like `self:`. The red team measured it on the LOB file. The designer would write `heading: invoiceNumber` identically on all twelve `Invoice details` compositions, which is the dead-weight signature. The designer's actual headings mix copy with state (the word "Invoice" followed by the phase, "awaiting approval"). And the wanted second line, the supplier name, is not the first secondary field on any of the twelve, so `subheading:` would be demanded on the first LOB surface. The v0.4.0 changelog had already named per-field header promotion as the placement judgment below `slot:`'s granularity. What replaces it costs no structural key: surface labels become ICU MessageFormat messages with field arguments. `InvoiceDecision: "Approve {invoiceNumber} from {supplierName}"`; `Budgivning: "{description}"`. Arguments resolve against scalar fields of the surface's composed views (`xm-label-arg-missing`, error), and the grammar is capped by lint to `{arg}` and `{arg, plural, …}`, because ICU `select` is a conditional and a conditional in the labels section is `when:` by another door. This covers every heading in all four testbeds and keeps headings where the spec already puts them: "a surface's on-screen heading is its label".

The rest of the labels extension is the largest practical gain of the inquiry, and it is copy, not interaction. Exception names become labelable keys: 25 distinct `x:` names on the LOB model and 9, 16 and 10 hand-written `Describe` strings in the three games move into the model, with zero new reserved keys. `$confirm` at command level carries the assent question. `$values` at field level labels declared enum values (`onHold` → "On hold"). Copy is never derivable, and only exception copy has any interaction-design pedigree (Nielsen's H9); none of it is an Interaction Model.

The remaining sense C candidates fall in one line each. Posture (read-only versus editable, sovereign versus transient): editable iff the surface composes a command; Cooper's postures are containers. Presentation modality (modal, drawer, inline, page edit): placement. Wizard steps: slices if there is intermediate state, concrete if there is not. Undo pairing: which command compensates which is behaviour, and xmlang asserting it is F2. Per-command hide versus disable: a design-system-wide rule in all five systems surveyed, restated. Optimistic versus confirmed feedback, message channel, loading thresholds: timing and transport, fixed once per design system in all seven systems surveyed, never per action. Status criticality per enum value (Fiori's `Criticality`, Carbon's status indicator): a closed semantic tier, not copy, not derivable, and it passes all five tests at n=1, so it is deferred, not rejected, with a token-naming convention doing the work until a second LOB model needs more.

## 7. The Defaults sub-table

What the inquiry produces in bulk is not vocabulary but a sub-table under Defaults, "Navigation and enablement defaults", stating what every interpreter and probe already computed identically:

| Row | Absent | Default |
|---|---|---|
| D-entry | an entry surface | The first surface in document order applicable to the persona with no `during`; a persona with none enters via the bare form of its first triggered command |
| D-menu | global navigation | The set D-entry ranges over, in document order; `during`-bound surfaces are reached via destinations and links; a terminal-phase surface offers return to entry |
| D-destination | `then` on a command item | The surface applicable to the viewer's persona composing the terminal view of the command's slice, in the new phase; if none or if it is the issuing surface, stay; a rejected command re-presents the issuing surface |
| D-selection | a selector within a `during` × `for` cell | When the cell holds one `during`-bound surface per persona, that surface. When it holds several, the surface composing the terminal view of the slice whose event fired last for the viewer; ties broken by offerable commands, then declaration order |
| D-enablement | enablement | A composed command is rendered only to personas whose `role` matches one of its trigger roles; within a surface, a command the Event Model shows would be rejected for this viewer in the current state independent of typed input is rendered disabled with the blocking exception's label, never hidden by state alone |
| D-required | required-ness of a prop | A command prop is required iff some rejection scenario rejects its absence |
| D-bulk | a bulk action | A command whose prop is a list of a composed view's item identity is offered over the selection |
| D-links | a link | A view field typed as another view's identity links to the surface composing that view for the persona |
| D-unidentified | a viewer resolving to no persona | Sees only surfaces with no `for:`, commands withheld, routed to the bare join or entry form where one exists |

This is the derived interaction stratum. It costs zero vocabulary, and it buys the thing the geometry experiment showed is worth buying: cross-transformer determinism. In that experiment the un-geometried spec left command placement transformer-variable, and the entire surviving residue of the `slot:` key was one Defaults sentence ("composed commands SHOULD render after all view content") that closed the variance for nothing. The same shape recurs here. The three clean-room probes split three ways on the unidentified viewer; the shipped games hide a withheld command while all three probes disabled it; D-unidentified and D-enablement close both. The implementation advice from the cost analysis is to state D-selection as prose and check compliance with a generated selector test, not to build a selection engine in the interpreter. The three existing selectors already comply as written.

## 8. The `during` defect, and what emlang owes

One spec defect appeared only because the LOB model has two deciders. The spec defines `during` against "when in the system's lifecycle the surface is active", and the reference parser unions every `State /` view's `phase` enum into one namespace. With an invoice lifecycle and a supplier lifecycle in one model, the second decider had to avoid the word `phase` and call its lifecycle `status`, at which point `during` could no longer split "show Deactivate" from "show Reactivate". The fix is additive: redefine `during` against the lifecycle of one decider, accept a map form `during: { Invoice: [draft, rejected] }` beside the list form, add `xm-ambiguous-phase` (error) for a bare value that exists in two deciders, and evaluate `xm-phase-uncovered` per decider. This is a sense B item that is neither `when:` in disguise nor derivable, and it is the cheapest change the testbed exposed.

The rest of what the inquiry found does not belong in xmlang at all. Eight debts are named for emlang, not solved here:

1. Trigger origin resolves to a view (`t: Role /View` as a reference or a declared bare form). 18 of 18 on the LOB model, 1 of 12 on the games.
2. True trigger sets: `t: host /Round results` beside `t: ⚙️ System / Next lot` where the shipped UI gives the host a button.
3. View parameters: `phaseFilter`, `query`, `asOf` are inputs to a projection, not projected data; every xmlang tier on them today is a category error.
4. Phase per decider, so a multi-decider model does not force the second decider to rename its lifecycle.
5. `compensates:` or `reverses:` on domain merits (Void and Post, Reactivate and Deactivate). xmlang must not derive `confirm` from it.
6. A scenario-coverage lint (`em-phase-transition-uncovered`); without it `xm-command-phase-mismatch` fires on coverage gaps and is noise, which is why that lint ships as info.
7. Actor identity on events as a stated convention, so D-selection's "fired for her" and `self:` resolve against the same prop.
8. Information completeness on result views: `Round scores` lacks `description` and `questionText`, so an ICU heading argument cannot resolve until the view carries the datum. The method's own rule is violated by the shipped screens.

## 9. What this says about the thesis

The first article mapped Garrett's five planes onto the two models and left one gap: the structure plane, where Garrett puts interaction design ("how the system will respond") and information architecture (nodes and their arrangement) ([Garrett, ACM Interactions](https://interactions.acm.org/archive/view/september-october-2003/the-elements-of-user-experience1)). This inquiry closes it, and the closure is narrower than the plane. Interaction design in Garrett's sense is the Event Model: the conceptual model is its views and commands, error prevention and recovery are its decider rules and compensating commands, "how the system responds" is command → event → view. Of information architecture, xmlang already had the nodes (surfaces) and the lattice (`during` × `for`); what was missing was the edges, and the edges are implied by the Event Model once the Defaults state how. Garrett's structure plane is the Event Model plus edges it implies.

The survivors of MBUI map one to one onto what was admitted. Statecharts survived by being the behaviour model as a state × event table; that is emlang's `phase` enum plus decider-true scenarios, which xmlang consumes through `during` and checks with one lint, never restates. Rails' `redirect_to` survived as a convention-default overridable in one line; that is D-destination plus `then`. `hx-confirm` survived as one flat closed attribute; that is `confirm`. Nothing that died (abstract containers, task algebras, transition rules with conditions) was let in, and the two candidates that came closest to the corpse pile (`heading:` as a one-field `slot: header`; `then` as the first edge of a sitemap) were the two the red team cut or fenced.

So the honest sentence is: the interaction stratum exists, and it is derived. What a designer adds to it is a friction bit and a return-to-worklist name. That is a confirmation of the first article's thesis on new ground, not a new stratum, and I would rather report a small true result than a large vocabulary.

## 10. The objections, and what would withdraw the keys

Three objections stand unresolved, and the article would be dishonest without them.

**Dual specification of destination.** The only LOB modeller we have wrote navigation into the slice's terminal `v:`; `then:` is a second home for the same fact. "Return, never advance" is a rule in prose, exactly where Cameleon's `(transition_task, next_PS)` rules and Figma's `Navigate to` stood before they grew conditions. The mitigations (the restates-default lint, the persona-mismatch error, the Non-goals on conditional and instance destinations) are also prose.

**One constructed testbed, never rendered.** Every LOB count rests on `lob-ap.*`, written by this team for this inquiry. Counts moved by a factor of two between the analysts' own models and the real file (4 of 9 became 2 of 21), and they may move again on a shipped product. No transformer has produced the LOB model's default experience, so there is no "live design equals default" proof of the kind that settled the geometry experiment. `confirm` and `then` are provisionally admitted; `xm-confirm-habituation` and `xm-then-restates-default` are the dead-weight instruments, as `xm-slot-restates-default` was.

**Derivability is borrowed from conventions emlang does not own.** The Defaults rows, the largest output, are computable only under the reference parser's conventions: the `State /` lane and its `phase` enum note, trigger text as an origin, slice element order as a timeline, identity props on events. The emlang spec states none of them; its root is `slices` and an element is one type key plus free-form `props`. Until emlang adopts items 1, 2, 4 and 7 of the debt list, "derivable" means "derivable by one implementation", which is F8 (a standard without implementers) relocated one layer down.

The tripwires are pre-registered, as they were for `slot:`. `then` is withdrawn if a second LOB model shows terminal `v:` and `then:` systematically disagreeing (the fix is the Event Model), or if any product needs a destination that depends on outcome or state (F1 has arrived; the key is withdrawn rather than extended). `confirm` is reverted if a second LOB model needs two grades of confirmation on one surface (the tier is on the slope, and the `slot:` rule applies). Status criticality is re-opened if a second LOB model wants a semantic state the token-naming path cannot carry. And D-selection's per-viewer clause is falsified if a fourth game or an LOB flow has a command-less surface with two exits.
